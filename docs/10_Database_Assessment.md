# GridSense AI — Database Assessment: Needed or Not?

**Direct answer: not needed right now, will become necessary at a specific, identifiable
point. Here's exactly where that line is.**

---

## Current state: no database, and that's a deliberate, working choice for now

The API reads `data/features/training_features.parquet` — a static file, committed to
git, generated by running the pipeline locally and redeployed manually. This works
because:

- Data volume is small (currently 600 rows after the memory-optimization trim — see
  System Architecture doc — well within what a flat file handles fine)
- Update frequency is manual and infrequent (you re-run the pipeline and redeploy when
  you want fresh predictions, not continuously)
- Read pattern is simple (filter by zone, take the last N rows — no complex queries,
  no joins at request time, no concurrent writes ever)

A database would add real operational complexity (a service to run, credentials to
manage, a schema to maintain, connection pooling to think about) for zero benefit at
this scale. Adding one now would be over-engineering, not professionalism.

## The specific point where this stops being true

A database becomes genuinely necessary when ANY of these becomes real:

1. **Live/continuous data ingestion.** If this moves from "run the pipeline manually,
   commit, redeploy" to "ingest new ENTSO-E/NTDC data every hour automatically," you
   need somewhere for that job to write that isn't a git commit. That's the actual
   trigger point — not data volume, not traffic, this specific workflow change.

2. **Multiple writers or write concurrency.** Right now, exactly one thing writes to the
   feature file: you, running a script, locally. If a scheduled job and a manual
   retrain could ever run at the same time, or if this needs to accept data from
   multiple sources concurrently, a flat file has no answer for that — a database does.

3. **Data volume exceeding what's comfortable to load fully into memory.** The recent
   memory investigation (System Architecture doc) found the API's baseline RAM footprint
   is already tight (~410MB against FastAPI Cloud Hobby's 512MB limit) BEFORE accounting
   for data growth. Real Pakistani NTDC/DISCO data, more zones, more asset-level
   granularity, or longer history will make this worse. At that point, a database that
   lets you query only what's needed (rather than loading everything into a pandas
   dataframe at startup) stops being a nice-to-have and starts being the fix for a real
   memory problem.

4. **Audit/history requirements.** TRD Section 3.2 (FR-8) requires every prediction to
   be logged with its input feature snapshot for auditability. This isn't implemented
   yet at all — when it is, that's naturally a database table (predictions_log or
   similar), not a file.

## What kind of database, when the time comes

Given the actual read/write pattern (time-series load/weather data, filtered by
zone+timestamp, no complex relational joins needed):

- **PostgreSQL** — the safe, boring, correct default. Handles the time-series pattern
  fine at this scale, has a mature ecosystem, and both FastAPI Cloud and Render offer
  managed Postgres add-ons, so this wouldn't add a third platform to manage.
- **TimescaleDB** (a Postgres extension) — worth considering specifically because this
  IS time-series data, if query patterns ever get more sophisticated (e.g., "give me a
  rolling 30-day average across all zones" type queries that a plain table would handle
  more awkwardly).
- Skip anything more exotic (a dedicated NoSQL store, a full feature-store product like
  Feast) — the actual complexity of this project's data doesn't justify that yet, and
  won't for a while even after a database becomes necessary.

## Recommendation

Do not add a database now. It solves a problem this project doesn't have yet, and adds
real operational surface area (another service, another set of credentials, another
thing that can go down) for a pilot/demo-scale deployment. Revisit this specifically
when you start real, scheduled ENTSO-E/NTDC ingestion instead of manual local runs —
that's the actual trigger, not a calendar date or a vague "eventually."
